  then unzip only `video/` + `thumb/`. Verified byte-identical index.html/tokens.css/

  `netlify deploy --allow-anonymous` **does work** and gives a live URL, BUT:
  - site is password-gated (password `My-Drop-Site`), and
  - it **expires after 60 minutes** unless claimed, and
  - `netlify claim` fails with `Unauthorized: could not retrieve project` without a
    logged-in account. So anonymous deploys are demo-only, not durable.
- `npm i -g netlify-cli` fails `EACCES /usr/local/lib/node_modules`. Install locally:
  `cd /tmp/nltool && npm i netlify-cli` → binary at `node_modules/.bin/netlify`.

## ffmpeg/ffprobe were missing (env reset)
- `apt-get install ffmpeg` → no root. `npm i ffmpeg-static` downloads **nothing**
  because npm's install-scripts policy blocks the postinstall.
- **Fix:** run the script by hand:
  `cd node_modules/ffmpeg-static && node install.js` → produces `ffmpeg` (76 MB).
  Copy to `~/bin/ffmpeg` (must be on PATH).
- `ffmpeg-static` ships **no ffprobe**. Use `npm i ffprobe-static`, binary at
  `node_modules/ffprobe-static/bin/linux/x64/ffprobe` → copy to `~/bin/ffprobe`.
- Without ffprobe, `npm test` fails exactly 1 check:
  "campuran mesin + musik ... video hasil mux tidak valid" (it probes the mux).

## Real bug found and fixed
- `GET /api/health` reported `ffmpeg: true` from
  `Boolean(process.env.FFMPEG_OK ?? 'true')` — always true, since the var is never
  set. It lied while ffmpeg was actually absent. Now calls `ffmpegAvailable()`
  (spawns `ffmpeg -version`). Commit `87f0784`.

## Perbaikan login studio (sesi ini)
Tiga bug yang saling menutupi, semuanya sudah diperbaiki + dites:
1. **Rate limiter per-IP.** `loginLimiter` dulu berkunci `req.ip`. Di balik
   proxy sandbox semua pengunjung berbagi satu IP, jadi 10 salah password dari
   orang lain mengunci semua orang (429). Sekarang dua kuota: per akun (10/menit)
   dan per IP (60/menit).
2. **Limiter hanya menghitung kegagalan.** `rateLimit()` sekarang punya

   localStorage, jadi login selalu 401. Sekarang memanggil `/api/setup` dan
   meminta password; tombol disembunyikan kalau `needsSetup:false` (409).
   Di mode demo tetap terbuka.
4. **Boot tidak lagi percaya localStorage.** `store.tsx` memverifikasi lewat
   `/api/me` sebelum menganggap user login; `logout` memanggil `/api/logout`.

Teks Pengaturan (`Models.tsx`) kini membedakan `backend aktif`/`sesi server`
vs `mode demo statis`/`sesi lokal` — sebelumnya selalu mengaku mode demo.

Terverifikasi: login lewat URL publik (proxy) 200 + cookie, `/api/me` benar,

## Deploy Docker/Render benar-benar rusak (diperbaiki)

Dua bug membuat SETIAP job di container berakhir `failed`, padahal `npm test`
hijau 174/174 dan host selalu sukses. Penyebabnya lingkungan, bukan logika:

1. `Dockerfile` tidak memasang `piper`, dan `assets/tts/*.onnx` di-gitignore.
   Akibatnya `ttsAvailable()` false → gate QA `narasi-ada` menolak (selalu,
   karena `localVoiceoverFor()` selalu mengisi voiceover).
   Perbaikan: venv `/opt/piper` + `pip install piper-tts==1.8.0`, model
   diunduh dari HuggingFace setelah `COPY . .` (kalau sebelum COPY bisa
   tertimpa), gagal unduh tidak menggagalkan build.

2. **ffmpeg 5.1 (Debian image) vs 9.0 (host)**. `norm()` =
   `loudnorm,aresample=48000` tanpa channel layout. ffmpeg 9 menebak layout,
   ffmpeg 5.1 gagal: "Cannot select channel layout for the link between
   filters". `muxAudio` mengembalikan `false` TANPA pesan → video tanpa audio
   → QA `ada-audio` menolak. Perbaikan: tambah
   `aformat=sample_rates=48000:channel_layouts=stereo` di ujung `mixNorm()`.

**Pelajaran penting**: tes integrasi audio TIDAK bisa menangkap bug ffmpeg
versi. Saya kembalikan bug-nya dan 175 tes tetap lulus karena host pakai
ffmpeg 9. Satu-satunya penjaga yang bekerja adalah tes struktural yang
memeriksa string filter (`tests/run.ts`, "rantai normalisasi campuran selalu
menetapkan channel layout"). Kalau mengubah filter ffmpeg, uji di container
(`docker build` + job nyata), bukan hanya `npm test`.

## Cara menguji image Docker dengan benar
`docker run -e WORKER_IN_PROCESS=1 -e STUDIO_DATA_DIR=/var/data -p 18080:8080`.
Tanpa `WORKER_IN_PROCESS=1` job menggantung di `queued` selamanya (worker
tidak jalan) — ini bukan bug, hanya env yang lupa diteruskan.
